## 2. Itemized Technical Reconciliation Log

### Item 1 (P0-1): Dual-Conduit in Upstream Mainline vs ZCOP Driver
- **Review Finding:** Upstream `drivers/net/dsa/yt921x.c` (`yt921x_chip_setup_dsa()`) computes `__ffs(priv->cpu_ports_mask)` and writes to a single register `YT921X_EXT_CPU_PORT` (`0x8000c`), proving that upstream mainline DSA does NOT support simultaneous dual CPU ports on YT9215.
- **Forensic Investigation:** Audited ZCOP's source tree (`zcop/immortalwrt` commit `7b307fa`). ZCOP implemented dual-conduit through an out-of-tree driver (`compatible = "motorcomm,yt9215-enhanced"`) with custom DTS properties (`motorcomm,secondary-conduit-user-mask = <0x8>`, `motorcomm,conduit-role`) and internal switch VLAN/forwarding matrix partitioning (`PORT_MEM` / `VLAN_MEM`).
- **Correction Made:** Proved that dual-conduit does NOT exist in clean upstream Linux mainline. Upstream baseline is strictly single-conduit (Port 8 via `eth1`). Dual-conduit is classified as an unupstreamed, experimental capability.
- **Evidence Level:** `SOURCE_VERIFIED` (for code difference); `REPORTED_UNVERIFIED` (for hardware dual-conduit).
- **Deliverable:** Created [`docs/M7.1/DUAL_CONDUIT_FINAL_RECONCILIATION.md`](file:///D:/vibecode/CR8808-CUSTOM-FIRMWARE/docs/M7.1/DUAL_CONDUIT_FINAL_RECONCILIATION.md).

### Item 2 (P0-2): SPI NAND Flash Hardware ID & Voltage Disambiguation
- **Review Finding:** Historical project documentation in `docs/02_DEVICE_BASELINE.md` recorded JEDEC ID `0xef 0xaa 0x21`, but the text labeled the chip as "W25N01GWZEIG" (which has ID `0xef 0xba 0x21` and 1.8V).
- **Forensic Investigation:** Cross-referenced saved device readback baseline against official Winbond datasheets and Linux `drivers/mtd/nand/spi/winbond.c`:
  - `0xef 0xaa 0x21`: **Winbond W25N01GV (3.3V)** (`W25N01GVZEIG`).
  - `0xef 0xba 0x21`: **Winbond W25N01GW (1.8V)** (`W25N01GWZEIG`).
- **Correction Made:** Resolved the contradiction without new SSH contact. Established that the physical flash chip is the 3.3V **Winbond W25N01GV** (JEDEC `0xef 0xaa 0x21`). The "GW" designation was a legacy community transcription error. Both GV and GW feature 1-bit on-die ECC (`NAND_ECCREQ(1, 512)`).
- **Evidence Level:** `DEVICE_READBACK_RECONCILED` / `SOURCE_VERIFIED`.
- **Deliverable:** Created [`docs/M7.1/NAND_IDENTITY_RECONCILIATION.md`](file:///D:/vibecode/CR8808-CUSTOM-FIRMWARE/docs/M7.1/NAND_IDENTITY_RECONCILIATION.md).

### Item 3 (P0-3): Wi-Fi DFS Architecture & Multidimensional Calibration Matrix
- **Review Finding:** Erroneous reference to a nonexistent standalone kernel module `ath11k_dfs.ko` and simplistic description of calibration data as "only containing RF power".
- **Forensic Investigation:** Verified upstream Linux kernel source code (`drivers/net/wireless/ath/ath11k/`). Radar detection logic (`dfs.c`) is compiled directly into `ath11k.ko`. DFS operates across a 4-tier pipeline: Hexagon Q6 firmware baseband radar detector $\rightarrow$ host `ath11k.ko` WMI parser $\rightarrow$ `mac80211`/`cfg80211` CAC state machine $\rightarrow$ `wireless-regdb`.
- **Correction Made:** Eliminated all references to `ath11k_dfs.ko`. Documented the true contents of `0:ART`: Target power curves, LNA noise figure gains, IQ imbalance amplitude/phase constants, baseband filter CFR coefficients, thermistor slopes, and MU-MIMO phase delta matrices. Labeled HE160 DFS as requiring physical RF testing.
- **Evidence Level:** `SOURCE_VERIFIED` (Driver architecture) / `REPORTED_UNVERIFIED` (HE160 DFS stability on CR8818).
- **Deliverable:** Created [`docs/M7.1/ATH11K_DFS_COMPATIBILITY_AUDIT.md`](file:///D:/vibecode/CR8808-CUSTOM-FIRMWARE/docs/M7.1/ATH11K_DFS_COMPATIBILITY_AUDIT.md).

### Item 4 (P0-4): NSS Incompatibility & Fallback Demarcation
- **Review Finding:** Asserting slow-path exception ring as a certainty when 8-byte DSA tags hit the NSS NPU parser.
- **Correction Made:** Refactored NSS parser analysis to enumerate all four potential hardware/firmware behaviors:
  1. Hardware offload compatible (fails due to unknown L2 EtherType).
  2. Hardware offload incompatible (bypasses ECM).
  3. Software fallback via exception ring to host CPU.
  4. Ingress packet drop by NPU parser filter.
  Stated clearly that only packet captures and debugfs counter telemetry on physical hardware can isolate which behavior occurs.
- **Evidence Level:** `INFERRED`.
- **Deliverable:** Updated [`docs/M7.1/NSS_FEASIBILITY_MATRIX.md`](file:///D:/vibecode/CR8808-CUSTOM-FIRMWARE/docs/M7.1/NSS_FEASIBILITY_MATRIX.md).
