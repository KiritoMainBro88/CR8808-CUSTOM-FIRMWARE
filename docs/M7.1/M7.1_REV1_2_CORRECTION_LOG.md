## 2. Itemized Technical Reconciliation Log (P0-1 to P0-6)

### Item 1 (P0-1): SPI NAND Flash Part Standardization at Family Level
- **Review Finding:** Revision 1.1 identified JEDEC ID `0xef 0xaa 0x21` as Winbond W25N01GV (3.3V), but incorrectly asserted the full commercial ordering code `W25N01GVZEIG`. JEDEC ID (`0x9F`) only identifies manufacturer, memory type (3.3V SLC), and capacity (1Gb); it does not encode package geometry (e.g. WSON8 `ZEIG` vs SOIC16 `SFIF` vs TFBGA24 `TBIR`).
- **Correction Made:** Standardized part designation across all project documentation to:
  $$\text{Winbond W25N01GV family – JEDEC EF AA 21 (3.3V, 1-bit on-die ECC)}$$
  All assertions of the `ZEIG` suffix are explicitly marked unverified without physical optical inspection of the silicon package marking.
- **Evidence Level:** `DEVICE_READBACK_RECONCILED` (Family & JEDEC ID) / `SOURCE_VERIFIED` (Datasheet & Driver). Package suffix marked `UNVERIFIED`.
- **Updated Files:** [`docs/M7.1/NAND_IDENTITY_RECONCILIATION.md`](NAND_IDENTITY_RECONCILIATION.md), [`docs/M7.1/WIFI_NAND_BOOT_RECOVERY_AUDIT.md`](WIFI_NAND_BOOT_RECOVERY_AUDIT.md), [`manifests/m7.1-sources.lock.yaml`](../../manifests/m7.1-sources.lock.yaml).

### Item 2 (P0-2): Reclassification of Six Caldata RF Parameters
- **Review Finding:** Revision 1.1 listed six analog RF calibration parameters (PA curves, LNA gains, IQ imbalance, CFR, thermistor slope, phase delta) as if their binary layout at offsets `0x1000` and `0x26800` were verified on CR8818.
- **Correction Made:** 
  1. Clarified that OpenWrt and the host Linux driver (`ath11k`) treat the factory calibration blocks extracted from `0:ART` (`0x1000` and `0x26800`, length `0x20000` = 128 KB) as **opaque raw binary blobs** (`cal-ahb-c000000.wifi.bin` and `cal-ahb-b00a040.wifi1.bin`). Zero host-side decoding or struct parsing is performed.
  2. Reclassified the six analog RF parameters strictly as **`THEORETICAL_RF_PROPERTIES / UNVERIFIED_ON_DEVICE`**. Acknowledged that while Qualcomm reference documentation notes these parameters exist inside closed firmware radio calibration tables, the exact binary layout, internal byte offsets, checksum headers, and decoding algorithms on CR8818 are unverified.
- **Evidence Level:** `SOURCE_VERIFIED` (Partition offset & length) / `THEORETICAL_RF_PROPERTIES / UNVERIFIED_ON_DEVICE` (Internal calibration structures).
- **Updated Files:** [`docs/M7.1/ATH11K_DFS_COMPATIBILITY_AUDIT.md`](ATH11K_DFS_COMPATIBILITY_AUDIT.md), [`docs/M7.1/WIFI_NAND_BOOT_RECOVERY_AUDIT.md`](WIFI_NAND_BOOT_RECOVERY_AUDIT.md).

### Item 3 (P0-3): Upstream DFS WMI Event, Firmware Disambiguation & Regulatory CAC
- **Review Finding:** Diagram used generic event name `WMI_RADAR_DETECT_EVENTID`; conflated IPQ5018 WPSS with QCN6102 target firmware; lacked regional regulatory CAC distinctions; HE160 was prematurely presented as an approved capability.
- **Correction Made:**
  1. Corrected upstream Linux `ath11k` radar event identifier to exact symbol:
     $$\mathbf{WMI\_PDEV\_DFS\_RADAR\_DETECTION\_EVENTID}$$
  2. Disambiguated firmware subsystems: IPQ5018 integrates Hexagon WPSS / Q6 for internal 2.4 GHz radio and bus control, while the external 5 GHz QCN6102 executes dedicated target radio microcode (loaded from `ath11k/IPQ5018/` or `ath11k/qcn6122/hw1.0/`). Radar PHY pulse detection for 5 GHz DFS is executed within QCN6102 target firmware.
  3. Added international regulatory CAC specifications: 60 seconds standard for general DFS channels; **10 minutes (600s)** mandatory for weather radar frequencies (5600–5650 MHz / Channels 120–128) under ETSI EN 301 893; **30 minutes (1800s)** Non-Occupancy Period (NOP).
  4. Formally designated HE160 (160 MHz) as a **`CONDITIONAL_ACCEPTANCE_TARGET / REPORTED_UNVERIFIED`**, strictly contingent upon future RF hardware test bench verification.
- **Evidence Level:** `SOURCE_VERIFIED` (Upstream symbol & driver pipeline) / `CONDITIONAL_ACCEPTANCE_TARGET` (HE160 DFS operation).
- **Updated Files:** [`docs/M7.1/ATH11K_DFS_COMPATIBILITY_AUDIT.md`](ATH11K_DFS_COMPATIBILITY_AUDIT.md), [`docs/M7.1/WIFI_NAND_BOOT_RECOVERY_AUDIT.md`](WIFI_NAND_BOOT_RECOVERY_AUDIT.md).

### Item 4 (P0-4): NSS Test Hypotheses & Unified Exception Pipeline
- **Review Finding:** Four NSS parser behaviors were presented as established possibilities rather than test hypotheses. Software fallback and exception ring were treated as separate mutually exclusive outcomes rather than a unified mechanism.
- **Correction Made:**
  1. Unified Exception Ring and Software Fallback into a single two-stage pipeline: Stage 1 (Hardware DMA Exception: NPU parser fails L2 parsing $\rightarrow$ enqueues packet to NSS Exception Ring) $\rightarrow$ Stage 2 (Host Driver Ingestion: `qca-nss-drv` dequeues packet, strips metadata, and feeds raw `sk_buff` into standard Linux network stack via `netif_receive_skb()` for CPU-bound software fallback).
  2. Reclassified all 4 scenarios as **`TEST_HYPOTHESIS`** (Direct NPU Offload, Connection-Bypass Software Route, Two-Stage Exception Ring $\rightarrow$ Software Fallback, Ingress Filter Drop).
  3. Established a comprehensive 6-point **`EMPIRICAL_TEST_MATRIX`** covering wire packet capture (`tcpdump` / TAP), NSS statistics (`/sys/kernel/debug/qca-nss-drv/stats/*`), dual-core CPU utilization (`mpstat` / `perf`), drop counters (`ethtool`), throughput (`iperf3`), and latency/jitter (`ping -f`).
  4. Strictly mandated that no conclusion on NSS behavior can be asserted without execution on physical silicon.
- **Evidence Level:** `TEST_HYPOTHESIS` (Parser behavior) / `EMPIRICAL_TEST_MATRIX` (Verification protocol).
- **Updated Files:** [`docs/M7.1/NSS_FEASIBILITY_MATRIX.md`](NSS_FEASIBILITY_MATRIX.md).

- **Review Finding:** OpenWrt 25.12.6 integrates Linux 6.12.112. Linux 6.12.117 and 6.18.63 were released on 2026-11-10. Need strict version discipline preventing out-of-sync kernel bumps.

  2. Pinned Track A Daily Driver to OpenWrt 25.12.6 release baseline (Linux 6.12.112 as integrated), tracking only OpenWrt target stable maintenance updates (e.g. 6.12.y backports).
  3. Pinned Track B Experimental to Linux 6.18.63 LTS exploration tree.
- **Evidence Level:** `SOURCE_VERIFIED` (Release manifests & kernel.org tags).

### Item 6 (P0-6): Dual-Conduit Silicon Capability vs Driver Implementation
- **Review Finding:** YT9215 silicon has hardware capacity for up to two GMAC connections, but upstream driver configures only one tagged CPU port (`0x8000c`). Hardware capability must not be equated with driver implementation.
- **Correction Made:**
  1. Formally demarcated Silicon Hardware Capability (YT9215 supports Port 4 internal GE PHY & Port 8 SGMII) from Upstream Driver Implementation (`drivers/net/dsa/yt921x.c` configures only a single tagged CPU port via `__ffs(cpu_ports_mask)` and `0x8000c`).
  2. Reclassified ZCOP dual-conduit across two distinct levels:
     - Driver Source Code & DTS Bindings: **`SOURCE_VERIFIED`** at repository level (`zcop/immortalwrt` commit `7b307fa`).
     - Actual Dual-Conduit Operation on Physical CR8808 Hardware: strictly **`REPORTED_UNVERIFIED`** (no line-rate physical traces or bi-directional switching benchmarks published).
- **Evidence Level:** `SOURCE_VERIFIED` (Repository code) / `REPORTED_UNVERIFIED` (Hardware execution on CR8818).
- **Updated Files:** [`docs/M7.1/DUAL_CONDUIT_FINAL_RECONCILIATION.md`](DUAL_CONDUIT_FINAL_RECONCILIATION.md), [`docs/M7.1/DSA_DUAL_CONDUIT_AUDIT.md`](DSA_DUAL_CONDUIT_AUDIT.md).
